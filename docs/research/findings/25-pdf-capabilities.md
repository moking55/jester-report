# T25 — ความสามารถ PDF ขั้นสูงใน Gotenberg

ตรวจเอกสาร: 13 พฤศจิกายน 2026 (ตรวจซ้ำกับ primary sources รอบ review)  
ขอบเขต: เอกสาร Gotenberg **9.x แบบ rolling**; [T02](02-engine-baseline.md) บันทึก release reference v9.4.1 (S23; ตรวจ release page แล้ว: v9.4.1 ไม่มี PDF-related change ระบุ มีแต่การแก้พฤติกรรม WebSocket ภายใต้ `--chromium-proxy-server`) และ v9.4.0 (S24; เพิ่ม `position` ให้ stamp). ไม่มีการตรวจ runtime, image digest หรือผลิต PDF จริง สถานะทุกความสามารถด้านล่างคือ **documented ตาม docs 9.x / runtime unknown** ไม่ใช่ผลทดลองหรือข้อกำหนดที่อนุมัติแล้ว

ป้ายสถานะ: **documented** = หน้า docs ระบุตรงตัว; **inferred** = ข้อสรุปของเราจากหลักฐานหลายข้อ; **unknown** = docs ที่ตรวจไม่ระบุ. docs 9.x ไม่ระบุว่า stage/route ใดเริ่มมีใน release ย่อยใด (หน้า pipe/remediate/validate/sign/timestamp/encrypt ระบุเพียง "9.x" และลิงก์ upgrade guide จาก 8.x) จึงไม่ยืนยัน version ราย capability ได้ นอกจาก `position` ของ stamp = v9.4.0

## 1. Capability matrix

ตัวตรวจในตารางเป็นแนวทางที่เสนอ ไม่ได้หมายความว่า tool หรือ validator ใดถูกรันแล้ว `/forms/pdf/info` และ HTTP 200 ไม่ใช่เครื่องยืนยันความถูกต้องของข้อมูลธุรกิจหรือ conformance

| Capability / กรณีใช้ | Route หรือ option (documented) | Version / prerequisite / ขอบเขต | วิธีตรวจที่เสนอ; runtime |
| --- | --- | --- | --- |
| รวม/เลือก/แยก PDF สำหรับชุดรายงานหรือภาคผนวก | `POST /forms/pdf/pipe` (`files`, `stages` JSON ที่จำเป็น, `archives`, `downloadFrom`); stages `merge`, `select`, `split`, `delete`, `insert`, `compose`; ทุก stage มี single route `/forms/pdf/{op}`; field `stages` ใช้ได้กับ Chromium/LibreOffice conversion ด้วย (screenshot, per-stage, read routes คืน 400) | 9.x; input เป็น PDF; ลำดับ stage มีผล (หมายเลขหน้าเปลี่ยนหลัง select/merge); `split` ให้หลายไฟล์ ตอบเป็น ZIP; stage ที่ rewrite ปฏิเสธ PDF ที่ signed (400) | `/forms/pdf/info` (page count, version, encrypted/tagged/linearized/form fields) + เทียบ text/image; **not-tested** |

หมายเหตุความสอดคล้องของ docs: หน้า routes (S08) ไม่ได้ลิสต์ route `sign`/`timestamp` แต่หน้า sign/timestamp ระบุ `POST /forms/pdf/sign` และ `/forms/pdf/timestamp` ตรง ๆ จึงถือเป็น documented จากหน้าเฉพาะ; หน้า convert-html ไม่แสดง field เดิมอย่าง `pdfa`, `pdfua`, `metadata`, `embeds`, `flatten`, `encrypt`, `watermark` และชี้ PDF/UA ไปที่ stage `remediate` — **unknown** ว่า 9.x ยังรับ field เดิมเหล่านั้นหรือไม่ จึงไม่ใช้ในข้อเสนอ ใช้ `stages`/routes ข้างต้นแทน

การอ้าง PDF/A/PDF/UA/Factur-X ในตารางเป็นความสามารถของ API ที่เอกสารระบุเท่านั้น ไม่ใช่ข้อยืนยันว่ารายงานใบเสนอราคา, sales หรือ purchase order ของ T01 ผ่านมาตรฐานใด ใน T01 ยังไม่มีข้อกำหนดว่าต้องมี form, signing หรือ e-invoice ตั้งแต่ MVP

## 2. Stage order และผลต่อเอกสาร

ตาม [PDF pipe 9.x](https://gotenberg.dev/docs/pdf/pipe) (S82), [remediate](https://gotenberg.dev/docs/pdf/remediate) (S83), [encrypt](https://gotenberg.dev/docs/pdf/encrypt) (S87), [sign](https://gotenberg.dev/docs/pdf/sign) (S85) — ทั้งหมด **documented**:

1. `decrypt` ต้องอยู่ต้นรายการ; `render`, `extract-attachments`, `extract-text` อยู่ท้ายรายการ stage ใช้ผลจาก stage ก่อนหน้า
2. ใน list หนึ่งมีได้อย่างมากหนึ่งครั้งต่อ `remediate`, `encrypt`, `sign`, `timestamp`
3. หลัง `remediate` ตามได้เฉพาะ `encrypt`, `optimize`, `sign`, `timestamp`, `render`, `extract-attachments`, `extract-text` จึงต้องทำ stage ที่เปลี่ยนเนื้อหาให้เสร็จก่อน remediate; PDF/A + PDF/UA ที่ compatible ต้องอยู่ใน `remediate` เดียว
4. หลัง `encrypt` ตามได้เฉพาะ `optimize`, `render`, `extract-attachments`, `extract-text`; หลัง `sign`/`timestamp` ตามได้เฉพาะ `sign`, `timestamp`, `render`, `extract-*` (หน้า sign ระบุแคบกว่าว่า sign ได้ครั้งเดียวต่อ list และตามด้วย `timestamp`/`render` — ใช้ข้อเข้มกว่า)
5. `encrypt` ไม่รวมกับ `sign`, `timestamp` หรือ `remediate` แบบ PDF/A/Factur-X; `decrypt` ไม่รวมกับ `sign`/`timestamp` (ต้อง decrypt แล้ว sign ในอีก request) — หมายเหตุ: PDF/UA-only remediate กับ encrypt ไม่ถูกห้ามตรง ๆ ในหน้าที่ตรวจ (**unknown** ว่าผลเป็นอย่างไร)
6. PDF ที่ **signed แล้ว**: stage ที่ rewrite และถูกปฏิเสธ (400) คือ `select`, `delete`, `insert`, `merge`, `split`, `compose`, `encrypt`, `decrypt`, `flatten-form`, `redact`, `remediate`, `convert-colors`, `flatten-transparency`, `optimize`; stage ที่ update แบบคงลายเซ็น คือ `rotate`, `stamp-text`, `stamp-image`, `stamp-pdf`, `set-form`, `set-metadata`, `set-bookmarks`, `attach`, `detach`, `autotag`, `sign`, `timestamp`; stage ที่ไม่แก้ไฟล์ คือ `render`, `extract-attachments`, `extract-text`
7. **การคง signature bytes ไม่ยืนยันว่าลายเซ็นยัง valid ใน verifier หรือสอดคล้อง certification/DocMDP policy** (**inferred**: docs ไม่พูดถึง certification policy) ต้องตรวจ revision/permissions/trust หลังแก้ทุกครั้ง
8. stage ที่เปลี่ยนโครงสร้างหน้า/เนื้อหา/metadata หรือรวมเอกสาร อาจเปลี่ยน tags, reading order, page numbering หรือ metadata (**inferred**); `remediate` มี rollback ของ fix ที่ทำให้หน้า/ข้อความ/รูปหาย และ `aggressive` อาจเปลี่ยนหน้าตา จึงต้องตรวจ output ภายหลัง ไม่สมมติว่า profile เดิมยังผ่านโดยไม่ validate

ลำดับที่เสนอเพื่อศึกษา (inferred, ไม่รัน): render/merge/select/stamp → set-metadata/set-bookmarks → remediate → optimize (ถ้าใช้) → sign → timestamp. หมายเหตุ: stamp/metadata/bookmarks ที่ทำก่อน remediate เป็นไปตามกฎ "remediate ต้องตามหลัง stage เปลี่ยนเนื้อหา" แต่ผลต่อ tag structure หลังกลับลำดับยัง **unknown**

## 3. ตัวอย่าง Profiles สำหรับ T26

- **PDF/A-2b** เป็นตัวอย่างศึกษาข้อกำหนดด้านการเก็บระยะยาวของเอกสารหน้าเดียว/ตาราง โดยไม่กำหนดว่าผลิตภัณฑ์ต้องใช้ profile นี้ (docs เองแนะนำ PDF/A-4 เมื่อไม่เลือก profile)
- **PDF/UA-1** เป็นตัวอย่างศึกษาการเข้าถึงของรายงานไทยและตาราง; machine checks และ human checks ต้องแยกกัน
- Docs อนุญาต pair `PDF/A-2b` + `PDF/UA-1` ในหนึ่ง `profile` list ของ remediation/validation ([remediate](https://gotenberg.dev/docs/pdf/remediate), [validate](https://gotenberg.dev/docs/pdf/validate)) pair ที่ถูกต้องมีเฉพาะ PDF/A-1/2/3 หรือ Factur-X กับ UA-1 และ PDF/A-4 กับ UA-2 pair อื่น 400 การอนุญาตคู่นี้เป็น documented capability ไม่ใช่หลักฐานว่ารายงานของเราผ่าน profile ใด

รายละเอียด validation plan อยู่ใน [T26](26-pdf-profile-validation.md); T27 แยกความเชื่อถือ certificate/key และการตรวจลายเซ็น ไม่มีการเลือก vendor, profile สุดท้าย หรือสร้าง test key ในรอบนี้
